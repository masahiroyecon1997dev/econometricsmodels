# リファクタリング

対応するCLAUDE.mdの方針: 2章（絶対に守るべき設計方針）、3章（リポジトリ構成）、6章（コーディング規約）、
9章（ドキュメント運用）、14章（判断が分かれる点は都度確認）、15章（コンテキスト管理）

このスキルは**対象範囲・変更方針をユーザーが都度指定する**ことを前提とする（自動で対象を網羅的に
洗い出して直す形にはしない）。既存の`review-rust`/`review-python`/`review-testing`が
「直近の差分」を指摘のみ行うのに対し、このスキルは**実装当時から蓄積した既存コード・ドキュメントを
横断的に対象**にし、指摘から適用まで一括で行う。

## 対象範囲・方針

$ARGUMENTS

## 観点（Issue #231 4章）

1. **重複ロジックの共通化**
   呼び出し箇所の性質上、分離したままが適切な場合は無理に共通化しない（IV実装時のA章共通基盤
   切り出しと同じ判断基準。`docs/planning/specs/panel-iv-issue-breakdown.md`参照）。
2. **パフォーマンス劣化箇所の指摘・修正**
   不要な`clone`・非効率なループ等。深い規約チェックは`rust-reviewer`/`python-reviewer`に
   委ねてよい（対象ファイルを明示して`/review-rust`・`/review-python`を呼び出す）。
3. **コメント内のIssue番号への言及・冗長な説明の削除／要約**
   実装当時の検討経緯（「Issue #NNNで〜」等）は、WHYが非自明で残す価値がある場合のみ要約して残し、
   単なる経緯の記録は削除する（`.claude/rules/rust-style.md`・`python-style.md`の
   コメント言語方針とは独立の観点であり、既存方針と矛盾しない）。
4. **不要になったファイルの削除**
   参照されていないことを`grep`等で確認してから削除する。
5. **ロジックを壊さないためのテスト追加提案**
   テスト自体の拡充は`review-testing`・`/test-new`に委ねる（このスキルは提案のみ行い、
   実際のテスト追加は別スキルで行う）。

上記に加えて、ディレクトリ構造の整理・ドキュメント（README/CLAUDE.md/`docs/spec/`・
`docs/planning/specs/`配下の仕様書）の整合性も対象に含む。

## 手順

1. **対象範囲の確認**
   $ARGUMENTSで指定された範囲・方針を確認する。範囲が曖昧、または複数の妥当な進め方が
   ありうる場合は、着手前にユーザーへ確認する（CLAUDE.md 14章、独自判断で埋めない）。

2. **現状調査**
   対象のコード・コメント・ディレクトリ構造・関連ドキュメントを読み込む。大量ファイルの
   横断調査が必要な場合は`Explore`エージェントに委譲し、メインセッションの文脈を汚さない
   （CLAUDE.md 15章）。

3. **リファクタリング計画の提示**
   上記観点ごとに見つかった項目をリストアップし、重要度（must fix / should fix /
   nice to have）を付ける。**ファイル削除・ディレクトリ移動・リネーム等の破壊的操作は
   個別に明示**する。計画をユーザーに提示し、実施内容について合意を得てから次に進む
   （このスキルは適用まで行うため、レビュー系スキルと異なり計画提示を省略しない）。

4. **適用**
   - コード修正: 対象言語の規約（`rust-style.md` / `python-style.md`）に従う。
   - コメント整理: 上記観点3の基準に従う。
   - ファイル削除: 参照有無を確認した上で`git rm`（追跡外ファイルは理由を確認してから削除）。
   - ディレクトリ移動・リネーム: 履歴を保持するため`git mv`を使う。
   - ドキュメント整理: `README.md` / `CLAUDE.md` / `docs/spec/` / `docs/planning/specs/`の
     該当箇所を更新する。手法の実装が完了済みで`docs/planning/specs/`に設計ノートが残っている
     場合、CLAUDE.md 13章の方針（完了した手法の仕様書は`docs/spec/`へ集約）に沿っているかも
     合わせて確認する。
   - **ロジックの挙動を変える変更（バグ修正含む）はこのスキルの範囲外**。気づいた場合は
     指摘に留め、対応要否を別途ユーザーに確認する（`engine/`層は特に慎重に扱う、
     Issue #231フェーズ7の方針）。

5. **検証**
   変更した層に応じて`cargo test` / `pytest`を実行し、デグレがないか確認する。
   `engine`/`engine_pybind`を変更した場合は`rust-reviewer`、`python_package`を変更した場合は
   `python-reviewer`をプロアクティブに呼び出す（CLAUDE.mdの既定運用と同じ）。
   **上記以外の層（`benchmark/`・`tests/`・ドキュメントのみの変更等）を含め、
   コード・ドキュメントに変更を加えた場合は必ず`/code-review`を実行する**
   （対象がコードのみ・専用レビューアーの対象外の層であっても省略しない。
   テスト・lintが通ることと、変更漏れ・余計な変更・ドキュメントの整合性崩れが
   無いことは別の観点であり、後者は`/code-review`でしか拾えない。実例:
   2026-08-22、ドキュメント編集時に隣接する別項目の見出し行を誤って削除した
   事故を`/code-review`のみが検知した）。指摘が出た場合は適用するか、
   対応不要と判断した理由を記録してから次の手順へ進む。

6. **コミット前の最終確認**
   ステップ5の`/code-review`が実際に実行され、指摘への対応（適用 or 対応不要の
   理由記録）が完了していることを確認してから、ユーザーにコミット可否を確認する。
   `/code-review`を省略したままコミットしない。

7. **記録**
   `docs/planning/specs/refactoring-issue231-progress.md`の該当フェーズに、変更ファイル一覧・
   判断結果・未解決事項を追記する。

## 完了条件

- 対象範囲について、該当する観点のチェック・適用が完了している
- 既存テスト（`cargo test` / `pytest`）がグリーン
- **`/code-review`を実行し、指摘への対応（適用 or 対応不要の理由記録）が完了している**
  （変更した層に関わらず必須。省略した状態で完了条件を満たしたと報告しない）
- 破壊的操作（削除・移動）はすべて事前提示・合意を経ている
- `docs/planning/specs/refactoring-issue231-progress.md`に記録済み

## 制約

- 指定された対象範囲外のファイルには手を出さない。
- ロジックの挙動を変える変更はこのスキルの範囲外（観点5参照）。
- コミット・プッシュは行わない（ユーザーの明示的な指示があった場合のみ、このスキルの外で行う）。
- **`/code-review`を実行せずにコミットを提案・実行しない**（レイヤー問わず必須、手順5・6参照）。
