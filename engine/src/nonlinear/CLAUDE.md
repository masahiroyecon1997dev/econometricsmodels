## 踏んだ罠（再発防止）

- **多重共線性（設計行列のランク落ち）の検出は `fit()` 冒頭の列ピボットQRランクチェックに一本化（Issue #279）**: Logit/Probit/Tobit の `fit()` は `method`（newton/bfgs/lbfgs）に関わらず、`run_solver` を呼ぶ前に `nonlinear::common::checked_design_matrix_qr(x_std)` を必ず通し、ランク落ちを `MleError::SingularDesignMatrix`（→ `ComputationError`）で弾く。**新しい MLE 手法の `fit()` を足したら、`standardize_columns`（または手法固有のスケーリング）後・`run_solver` 前にこの呼び出しを入れること**。Logit/Probit は QR 解を `ols_based_initial_params`（LPM の IRLS 1ステップ相当の warm start）で初期値にも使う（Tobit は `ols_initial_params` が QR 解を `β` 初期値に、残差を `σ` 初期値にする）。旧来のゼロベクトル初期値では検出経路が `method` ごとに分かれ（newton は `newton_step` 内 QR、bfgs/lbfgs は収束後の `observed_information_cov_params`）、過去に bfgs だけ検出漏れした実バグがあった。回帰ガードは `logit.rs`/`probit.rs` の `fit_returns_singular_design_matrix_error_for_perfectly_collinear_design_matrix`、`common.rs` の `checked_design_matrix_qr_*` / `ols_based_initial_params_*`。
- **`Estimator::fit()` 冒頭で `crate::parallelism::ensure_serial()` を呼ぶ（Issue #283）**: faer のグローバル並列度を `Par::Seq` に固定する。理由・背景の詳細は `engine/src/linear/CLAUDE.md`「faerのグローバル並列度」と `.claude/rules/rust-style.md`「パフォーマンス」節を参照（tall-skinny な設計行列での暗黙全コア並列化が多コア機・負荷下で 20〜200倍遅く不安定になる）。Logit/Probit/Tobit の各 `fit()` に追加済み。**新しい MLE 手法の `fit()` を足したら呼び出しを忘れないこと**（`nonlinear/common.rs` の `run_solver` 系ではなく、各手法の `fit()` エントリで呼ぶ）。回帰ガードは `logit.rs` の `fit_pins_faer_global_parallelism_to_seq`。
- **大標本Newtonの収束判定 `tol` は総和勾配に対する絶対しきい値で n スケールしない（Issue #291、修正済み）**: `common.rs` の `FaerNewton::terminate` の主判定は `l2_norm(gradient) < tol`（既定 `1e-6`）。勾配は n 個の観測スコアの総和なので収束点近傍で桁落ちが支配的になり、達成可能な勾配L2ノルムの「床」がデータ依存で `tol` を超える（`moderate_censoring` Tobit の実測で `n=200_000` は床≈`1·tol`、`n=1_000_000` は床≈`36·tol`）。この状態でコスト関数が浮動小数点の底（`|cost|≈1e5`, ULP≈`1.5e-11`）に達すると、`regularized_newton_step` の LM ラダー（`λ` を `0→1e-3→×4→…`）がどの `λ` でも `candidate_cost < cost`（狭義）を満たせず、**修正前は無条件で `Err(MleError::SingularHessian)` を返していた**（`ComputationError: the Hessian is singular and cannot be inverted`。実際には収束点の `-H` は良条件で、メッセージは誤り）。#284（Probit 大標本で Hessian 特異）と同系統。
  - **修正内容**: `regularized_newton_step` の戻り値を `RegularizedStep` enum にし、LM ラダー全失敗時に **`λ=0`（正則化前）の `newton_step` が可逆だったか**で分岐する。可逆なら `RegularizedStep::NoProgress`（真に特異ではなく、コストが底に達しただけ）、不可逆なら従来どおり `SingularHessian`（完全な多重共線性等、`run_solver_newton_returns_singular_hessian_error` の `SingularHessianProblem`）。`FaerNewton::next_iter` は `NoProgress` を受けたとき、次の3条件がそろえば `stalled_at_optimum` を立て、`terminate` がそれを見て `SolverConverged` を返す（現在点をそのまま返し、生ステップは適用しない）:
    1. 生の Newton ステップを1回進めても勾配ノルムが実質的に減らない（`≥ NEWTON_STALL_GRAD_RATIO=0.9 · 前反復`）
    2. 勾配ノルムが収束目標の近傍（`< NEWTON_STALL_GRAD_FACTOR=1e4 · tol`）。最適点から遠い停滞・発散を除外
    3. **コスト関数（負の対数尤度）の Hessian が正定値**（`cost_hessian_is_positive_definite`、`llt`）。`newton_step` の列ピボット QR は可逆性しか見ないため、鞍点（可逆だが不定符号。Tobit の `(β, logσ)` 尤度は大域凹でない）で `NoProgress` が返っても収束扱いにしない。3条件が揃わなければ生ステップを適用して反復継続 → `max_iter` 到達で `NonConvergence`。
  - **切り分けの決め手（調査時）**: 同一データで `tol` を `1e-5` 以上に緩める / `method="lbfgs"` にすると収束し、`observed_information_cov_params`（= `-H` の Cholesky 逆行列）も成功する。`cov_type="opg"` でも同じエラーが出る（opg 経路は `neg_hessian_inverse` を呼ばない）ことから、失敗は SE 計算ではなく最適化ループ内。
  - **Logit/Probit は挙動不変**: 尤度が大域凹で LM ラダー全失敗（`NoProgress`）に入らない。既存の `SingularHessian` テスト（完全な多重共線性）は `λ=0` の Hessian が不可逆なので従来の分岐に落ちる。engine 428 テスト・nonlinear pytest 421 テストが非リグレッションでパス。
  - **再現/検証データ**: `benchmark/nonlinear/datasets.py` の `generate_censored_regression_dataset("moderate_censoring", n, k=5, seed)`。`n=200_000 seed=1` は数値微分MLE（scipy BFGS）と logLik が `-204908.222939`（相対誤差 2.6e-13）で一致、`n=1_000_000 seed=42` も logLik 相対誤差 2.6e-13・σ 相対誤差 6e-9 で一致。Rust ユニットテストは `common.rs` の `run_solver_newton_converges_when_cost_hits_floating_point_floor_above_gradient_tol` / `..._stalled_at_optimum_reports_converged_even_without_raising` / `..._does_not_treat_flat_cost_with_large_gradient_as_converged`（条件2ガード）/ `..._does_not_treat_indefinite_hessian_stall_as_converged`（条件3=正定値ガード）。`FloatingPointFloorProblem` / `FlatCostLargeGradientProblem` / `IndefiniteHessianStallProblem` は機構とガードの模擬。
  - **大標本の回帰ガード（対応済み）**: 実 Tobit 経路を大標本で通す自動チェックは `performance/compare_tobit.py` の `n_sweep_engine_only=(200_000, 1_000_000)`（`1d0851a`）が担う。n=1,000,000（seed=42）が #291 の再現点で、`_run_isolated` の `check=True` により再発すれば benchmark ジョブが失敗する。発火は `benchmark_performance.yml` のタグ push + **dev⇒main の PR**（`5e75477`、リリースゲート）+ workflow_dispatch。限界（単一 seed=42 / 例外のみ捕捉 / silently-wrong な収束は対象外）は `compare_tobit.py` docstring・`docs/performance/tobit.md` 参照。

- **BFGS（`method="bfgs"`）はargmin組み込みソルバーを使わず自前実装`FaerBfgs`（Issue #285、`common.rs`）**: newton・statsmodelsの同methodと比べBFGS/LBFGSが桁違いに遅い問題（実測: n=1,000,000でnewton 0.65s・bfgs 11.21s・lbfgs 23.91s）の根本原因は、組み込みBFGS（`argmin::solver::quasinewton::BFGS`）の初期逆Hessianが単位行列（スケール`O(1)`）固定なのに対し、Logit/Probit/Tobitの尤度Hessianは`n`個の観測のスコアの和（`X'WX`型）でスケールが`O(n)`であること。乖離が`n`に対して桁違いに開くため、最初の探索方向が暴走しline searchが1反復あたり多数の関数評価を消費し、外側反復回数自体も`n`に対して増加する（実測: n=100,000→1,000,000でNewtonの反復回数は4のまま一定なのに対し、組み込みBFGSは15→22と増加）。
  - **対処**: Nocedal & Wright *Numerical Optimization* 6.1節の標準的な対策（1回目の反復でline searchが実際に受理したステップから秘密方程式ペア`(s₀,y₀)`を作り`γ=(y₀ᵀs₀)/(y₀ᵀy₀)`で初期逆Hessianをself-scalingしてからrank-2更新する）を適用したいが、この手法は「1回目の反復の終わり（rank-2更新の直前）」というタイミングにフックする必要があり、argmin組み込みBFGSの公開APIには存在しない（`linesearch`フィールドがprivate、`initial_step_length`は一度設定すると全反復で同じ固定値が使われ続ける。argmin自身の`BFGS::next_iter`にこの手法に相当するコードがコメントアウトされた壊れた状態〈`self.inv_hessian`という現存しないフィールドを参照〉で残っているだけで機能していない）。**`FaerNewton`と同じ理由（組み込みソルバーが必要な制御点を公開していない）で`FaerBfgs`として自前実装した**（argminの`Solver`トレイトを直接実装し、`Executor`/`MoreThuenteLineSearch`自体は流用する設計は`FaerNewton`と同型）。あわせて1回目の反復専用のline search初期ステップ幅を`min(1,1/‖g₀‖)`に調整し、2回目以降は標準の`alpha=1.0`に戻す。
  - **secant条件`yᵀs>0`を満たさない場合はrank-2更新をスキップし現在の逆Hessian近似を維持する**（標準的なBFGSの安全策、正定値性を壊さないため）。閾値は絶対値`f64::EPSILON`のまま（`‖s‖‖y‖`に対する相対値は**不採用**）: rust-style.md「線形代数」節の特異性判定の方針に倣い一度は相対閾値を試したが、`generate_binary_choice_dataset("baseline", link="logit", n=1_000_000, k=5, seed=42)`で実測したところ反復回数・実行時間がかえって悪化した（n_iter 17→23、15.0s→20.7s）。secant条件は「行列の特異性判定」ではなく「BFGS更新の正定値性を保つための降下方向チェック」で性質が異なるため、この方針をそのまま転用しないことにした（`bfgs_updated_inv_hessian`のdocコメント参照）。
  - **`terminate()`は勾配ノルム基準に加え、組み込みBFGSと同じコスト変化ベースの副次判定（`|prev_cost-cost|<f64::EPSILON`）も明示的に踏襲する**: この判定を落とすと`fit_non_classical_cov_types_work_with_bfgs_and_lbfgs`（Tobit）・`fit_returns_separation_suspected_error_for_near_separation_data`（Logit）が`NonConvergence`にリグレッションすることを実測で確認済み。near-separation等の退化した尤度面では、line searchがこれ以上進めずコストが完全に変化しなくなる一方、勾配ノルムがまだ`tol`を下回らないことがあるため、この副次判定が実質必要（Newton側の#291と類似の「勾配ノルム基準だけでは大標本・退化データで発火しない」問題だが、Newtonのような専用のstall検出ロジックではなく組み込みBFGSと同じ単純な判定をそのまま踏襲する形で対処した）。
  - **`Method::Lbfgs`は対象外**: argmin 0.11.0のLBFGS実装は初期曲率スケール（内部の`s`/`y`履歴、`γ`計算）を外部から注入する公開APIが無く（privateフィールド、対応するビルダーメソッド無し）、同じ手法を適用できない。line searchの初期ステップ幅で代用しようとしても全反復共通の固定値になり、2回目以降の反復（LBFGS内部の動的`γ`で既に正しくスケールされている反復）を悪化させるリスクがあるため見送った（ユーザー確認済み）。
  - **効果は限定的**: 公式ハーネス（`performance.compare_logit --worker`、n=1,000,000・k=5・classical）での再測定でBFGSは約6〜7%の改善（組み込み比、#279後の状態から）にとどまり、newton・statsmodels（bfgs 1.47s）とは依然1桁以上の差が残る。完全な解決には至っていない（`docs/performance/logit.md`「結果: method軸」参照）。
  - **回帰ガード**: `common.rs`の`bfgs_rank2_update_matches_hand_computed_values_for_non_diagonal_case`（rank-2更新の数式検証）・`bfgs_updated_inv_hessian_*`（self-scaling・secant条件スキップ・1回目限定の適用範囲を個別に検証）・`run_solver_bfgs_converges_to_known_minimum`（既存の統合テスト）。Logit/Probit/Tobitの既存`fit()`テスト（method=bfgs含む）は非リグレッションでパス。
- **`bfgs`/`lbfgs`は`tol`を観測数`n`で正規化した基準を使う（Issue #285、上記の`FaerBfgs`自前実装だけでは解決しなかった残タスク）**: 上記の自前化後もBFGS/LBFGSがNewtonから桁違いに遅い根本原因は、`tol`の意味論そのもの（総和勾配に対する絶対閾値で`n`スケールしない、#291と同根）にあった。`newton`は2次収束のためこの影響をほぼ無償で吸収するが、`bfgs`/`lbfgs`は超1次収束のため`n`が大きいほど同じ絶対閾値を満たすのに必要な反復が増える。statsmodels（scipy）は最適化前に対数尤度・スコア・Hessianを`n`で割ってから最適化するためこの影響を受けない。
  - **対処**: `run_solver`（`nonlinear/common.rs`）が`method=Bfgs/Lbfgs`のときのみ、呼び出し元から渡された`n_obs`（観測数）を使って`tol * n_obs`を実効的な絶対閾値として`FaerBfgs`/組み込み`LBFGS`へ渡す（＝「観測あたり平均勾配」基準への正規化）。`method=Newton`は`tol`をそのまま渡す（絶対閾値、変更なし）。`run_solver`のシグネチャに`n_obs: usize`引数を追加し、Logit/Probit/Tobitの`fit()`は`input.y().nrows()`を渡す。
  - **既定値も`method`により異なる（`engine_pybind`側）**: `newton`は`tol=1e-6`（絶対閾値、従来通り）、`bfgs`/`lbfgs`は`tol=1e-8`（正規化基準）。`LogitOptions`/`ProbitOptions`/`TobitOptions`の`tol`引数は`Option<f64>`にし、`None`（未指定）のとき`method`文字列を見てどちらの既定値を使うか`new()`内で分岐する。**共有の単一既定値は採れない**: `newton`の既定を`1e-8`（絶対閾値のまま）に締めると大標本で無視できない速度低下（実測: n=1,000,000で0.98s→3.15s、n_iter 4→7）が起きる一方、`bfgs`/`lbfgs`の既定を`1e-6`（正規化基準）に緩めると`n=500`の精度検証テストを壊す。
  - **`newton`にも同じ正規化を適用する案は検証の上で不採用**: 一度は`FaerNewton`にも`tol*n_obs`を適用して試したが、`near_separation`（Logit/Probit）・`heavy_censoring`/`interval_censoring`（Tobit）等の`RTOL=1e-8`精度検証テストが28件失敗した（例: `interval_censoring/hc1/wald_statistic`で相対誤差6.5e-6）。`newton`は2次収束による高精度が前提でテストが組まれているため、正規化によって実効閾値が`n`倍に緩むとこの精度マージンを食いつぶす。ユーザーに実測結果を報告の上、`newton`は非正規化のまま維持する方針を確定した。
  - **効果**: 公式ハーネス（`performance.compare_logit --worker`、n=1,000,000・k=5・classical、単一スレッド）で`bfgs`は15.0秒→0.73秒（約20倍）に改善。`newton`は0.63秒で不変。`lbfgs`は17.5秒で旧実装（18.2秒）からほぼ改善しない——同じ実効閾値でも`bfgs`より収束に必要な反復数がずっと多いため（実効閾値`1e-2`相当で`bfgs`は6反復・`lbfgs`は17反復）、`bfgs`に効いた既定値の正規化だけでは`lbfgs`は速くならない。`lbfgs`固有により緩い既定値が必要かどうかは別Issueで検討する（今回のスコープは正規化という仕組みの導入のみ、ユーザー確認済み）。
  - **小標本での精度は既定値`1e-8`で維持される**: `tests/fixtures/benchmarks/logit.json`の`baseline`（`n=500`、`RTOL=1e-8`）で、`bfgs`の`tol=n*1e-8=5e-6`は`tol=1e-6`（旧既定の絶対閾値）と完全に同じ反復回数（7）・精度（相対誤差1.77e-9）。`tol=n*1e-6`（100倍緩い設定）だと相対誤差3.84e-6まで悪化する——既定値を`1e-6`ではなく`1e-8`にした理由。
  - **回帰ガード**: `common.rs`の`run_solver`呼び出し全箇所（テスト含む）に`n_obs`引数を追加済み（合成問題のテストは`n_obs=1`で従来の絶対閾値と同じ挙動を維持、`Method::Newton`は`n_obs`を無視するためどの値でも無害）。Logit/Probit/Tobitの`fit()`テスト・pytest全体（1164件）・cargo test全体（647件）が非リグレッションでパス。既存の`fit_returns_separation_suspected_error_for_near_separation_data`（Logit、method別`max_iter`）も変更なしでパス（正規化後の実効閾値でも同じ反復回数域でSeparationSuspectedが発火することを確認済み）。
    - **正規化ロジック自体を直接検証するテストを追加（rust-reviewer指摘、当初は全テストが`n_obs=1`で正規化ロジック自体が未検証だった）**: `common.rs`に`run_solver_bfgs_scales_effective_tol_by_n_obs`/`run_solver_lbfgs_scales_effective_tol_by_n_obs`（`tol=1e-9,n_obs=1000`と`tol=1e-6,n_obs=1`が同じ実効閾値になり同じ収束点・反復回数に達することを検証）・`run_solver_newton_ignores_n_obs`（`n_obs`をどう振っても`Method::Newton`の結果が変わらないことを検証）を追加。`engine_pybind`側にも`LogitOptions`/`ProbitOptions`/`TobitOptions`それぞれに`new_resolves_tol_default_based_on_method_when_tol_is_none`（`tol=None`のとき`method`別の既定値`1e-6`/`1e-8`が解決されることを検証）を追加。
    - **既知の限界（ドキュメント化のみ、rust-reviewer指摘）**: `LogitOptions`等の`tol`/`method`フィールドは`#[pyo3(get, set)]`で構築後も可変で、`tol`のmethod依存デフォルト解決はコンストラクタ内で一度だけ実行される。構築後に`method`だけをセッターで変更しても`tol`は再解決されない（例: `method="newton"`で構築後`tol`が`1e-6`に解決され、その後`opts.method = "bfgs"`と代入しても`tol`は`1e-6`のまま——本来の`bfgs`既定`1e-8`より100倍緩い実効閾値になる）。`tol`フィールドのdocコメントに明記済み。実装での自動再解決（setterのオーバーライド等）は見送った（`method`/`tol`の順序に依存しない自己記述的なオプション構築を推奨する運用上の注意に留める）。
