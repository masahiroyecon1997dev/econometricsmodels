# リファクタリング候補の洗い出し

対応するCLAUDE.mdの方針: 5章（リファクタリング候補はGitHub Issueに起票、Issueは英語）、
14章（判断が分かれる点は都度確認）、15章（大量ファイル調査はサブエージェントに委譲）

このスキルは**候補の発見・提示・Issue起票**までを担当し、**コードは一切変更しない**
（承認後のGitHub Issue起票・コメント追記のみ例外）。適用は`.claude/skills/refactor`に委ねる。
コード解説の過程で気づいた候補を起票する場合も、このスキルの手順に従う。

## 対象

$ARGUMENTS

範囲が曖昧な場合や広すぎる場合（リポジトリ全体等）は、着手前にユーザーへ確認し、
層・ディレクトリ単位に絞る。

## 観点

観点の正本は`.claude/skills/refactor/SKILL.md`の「観点」節（重複ロジックの共通化・
パフォーマンス劣化箇所・コメント内のIssue番号言及や冗長な説明・不要ファイル・
テスト追加提案・ディレクトリ構造／ドキュメントの整合性）。ここには複製しないので、
実行時に必ずそちらを読んで従う。

発見側として追加する取り扱い:

- **ロジックの挙動を変える問題（バグ疑い含む）はリファクタリング候補に混ぜない。**
  「挙動に関わる指摘」として別枠で報告し、対応要否はユーザーに委ねる（`engine/`層は特に慎重に）。
- 重要度は`refactor`と揃えて must fix / should fix / nice to have を付ける。
- 根拠（`grep`での参照有無の確認結果等）を確認できていない項目は、断定せず「要確認」と明記する。

## 手順

1. **対象範囲の確認**
   上記「対象」を確認する。曖昧なら着手前にユーザーへ確認する（14章）。

2. **調査**
   対象のコード・コメント・構造・関連ドキュメントを読む。多数ファイルにまたがる場合は
   `Explore`エージェントに委譲し、メインセッションの文脈を汚さない（15章）。
   系統別のネストCLAUDE.mdに設計判断の理由が書かれている箇所は、意図的な構造として
   候補から外す。

3. **候補の提示**
   候補を、対象（ファイル・行）／内容／重要度／気づいた経緯（根拠）が分かる形で
   一覧にして提示する。「挙動に関わる指摘」は別表にする。
   候補が無ければ「今回は無し」と明示する（無言で省略しない）。

4. **既存Issueの照合**
   `gh issue list`・`gh issue view`で、候補と重複・関連するオープンIssueが無いか調べ、
   結果を次の確認の材料にする。

5. **起票方針の確認（必須）**
   Issueを作る前に、次を**ユーザーに確認して合意を得る**。独自判断で決めない。
   - どの候補を起票対象にするか（見送る候補はどれか）
   - 候補をどうまとめるか（1つのIssueにまとめる／テーマ・層ごとに分ける／1候補1Issue）。
     関連する候補は1つにまとめるのが基本（5章）だが、複数候補が見つかった場合は
     まとめ方の案を提示した上で選んでもらう
   - 既存のオープンIssueで扱える候補は、新規ではなくコメント追記にするか
     （手順4の照合結果を示して確認する）
   - 「挙動に関わる指摘」を起票するか、会話内の報告に留めるか

6. **起票**
   手順5で合意した内容どおりに、`gh issue create`（新規）または`gh issue comment`（追記）で
   起票する。
   - 本文は**英語**（リポジトリがpublicなため、5章）。
   - 対象（ファイル・行）／内容／重要度／根拠を含め、後から着手する人が文脈なしで
     理解できる書き方にする。
   - 起票前に、タイトル・本文・ラベル等の最終案をユーザーに見せて確認する。
   - 起票したIssueのURL・番号を報告する。

7. **次の一手の案内**
   適用したい候補があれば、`/refactor`に起票済みのIssue番号または範囲・方針を渡して
   進められることを案内する（このスキルでは適用しない）。

## 完了条件

- 対象範囲について全観点の確認を終え、候補（または「今回は無し」）を提示している
- 起票対象・まとめ方・新規／追記の別についてユーザーの合意を得ている
- 合意どおりに起票し、Issue番号またはURLを報告している
  （起票しない判断になった場合は、その旨を明示する）

## 制約

- 対象コード・ドキュメントは変更しない（適用は`refactor`スキル）。
- ユーザーの合意なしにIssueを作成・コメントしない。
- コード・コメント・仕様書にIssue番号を書き込まない（6章）。起票後の紐付けはIssue側で行う。
