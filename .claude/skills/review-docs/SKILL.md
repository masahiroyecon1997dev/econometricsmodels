# 公開ドキュメントの校正・校閲

対応するCLAUDE.mdの方針: 2章（比較・推奨を自己判断で変えない）、5章（Issueは英語・承認後に起票）、
13章（公開ページは英語、`docs/spec/`等への参照を書かない）、14章（判断が分かれる点は都度確認）、
15章（大量ファイル読み込みはサブエージェントに委譲）

公開ドキュメントを変更したときに、ユーザーの依頼（`/review-docs`または「校閲して」等の指示）で呼ぶ。
変更しただけでは自動実行しない。このスキルは**指摘の発見・提示・Issue起票**までを担当し、
**ドキュメントは一切変更しない**（承認後のGitHub Issue起票のみ例外）。修正は指摘を見たうえで別途依頼する。

チェック観点・出力形式の詳細は2つのサブエージェントの定義を単一ソースとする（ここには複製しない）。

| エージェント | 担当 |
|---|---|
| `docs-prose-reviewer`（`.claude/agents/docs-prose-reviewer.md`） | スペル・文章の誤り、ユーザー視点でのわかりやすさ、ドキュメント全体の構成 |
| `docs-accuracy-reviewer`（`.claude/agents/docs-accuracy-reviewer.md`） | 数式・統計学の正しさ、実装との整合、他パッケージへの言及の事実性・公平性 |

## 対象

$ARGUMENTS

- 指定なし: `git diff`（作業ツリーと、リリースブランチ上の未コミットの変更）で変更された公開ページ。
  変更が無ければ`git diff <基点>...HEAD`の基点をユーザーに確認する（独自に決めない）。
  `python_package/`のdocstringや`engine_pybind`の`///`が変更されている場合も、APIページに描画される
  公開docstringなので対象に含める。
- ファイル・ディレクトリ: 指定されたもの。
- `all`: 公開ページ全体。

**公開ページ**: `docs/index.md`・`docs/getting-started.md`と`docs/{usage,api,guide,methods}/`配下
（`docs/mkdocs.yml`の`exclude_docs`で外れる`docs/spec/`・`docs/planning/`・`docs/performance/`は対象外。
指定されても対象外であることを伝える）。生成物の`docs/guide/error-codes.md`・`docs/guide/performance-results.md`と
`docs/guide/performance.md`の生成ブロックは本文を校正しない（生成元の問題として扱う）。

## 手順

1. **対象の確定**
   上記から対象ページの一覧を作り、ユーザーに示す。範囲が広すぎる場合（`all`等）は、
   後続の分割方針（手順2）も併せて示す。

2. **サブエージェントへの委譲**
   2つのエージェントを**並列に**起動し、対象ページ（と、差分がある場合は変更箇所）を渡す。
   - 対象が多いときは文脈を守るため分割する。`docs-accuracy-reviewer`は手法ごと
     （`usage/`・`api/`・`methods/`の同名の3ページをまとめて）と`guide/`・トップ系ページに分け、
     `docs-prose-reviewer`は手法ごと／`guide/`・トップ系ページ／全体構成（nav・`index.md`・`getting-started.md`
     と手法間の構成の揃い方）に分ける。分割した呼び出しも可能な限り並列にする。
   - 分割時も他パッケージ言及の一覧は`docs-accuracy-reviewer`の結果を集約する。

3. **結果の統合**
   - 同じ箇所への指摘の重複は1つにまとめる（例: 文章の問題と事実の問題が同一箇所なら、事実側を主にする）。
   - 各エージェントの「引き継ぎ」は、もう一方の結果と突き合わせて取り込む。
   - 「挙動に関わる指摘」（文書が正しく、実装が誤っている疑い）は、ドキュメントの指摘と混ぜず別表にする。
   - 重要度は must fix / should fix / nice to have。確信度（確認済み／要確認／要Web確認）を残す。
   - 該当なしのカテゴリは「指摘なし」と明記する。

4. **Web検索による事実確認（ユーザー確認が必須）**
   `docs-accuracy-reviewer`が「要Web確認」とした他パッケージ言及（および確信度が「要確認」の
   他パッケージの挙動に関する主張）がある場合、検索する**前に**次をユーザーへ示して許可を得る。
   - 確認したい主張（場所・引用）と、検索語・見る予定の情報源（公式ドキュメント、ソースのリポジトリ等）
   - 許可が得られた主張だけを`WebSearch`/`WebFetch`で確認する（このスキルの`allowed-tools`には
     入れておらず、実行時に権限確認も出る）。
   - 確認結果は、結論・情報源のURL・確認した版を残す。**一次情報（公式ドキュメント・ソース）で
     確認できなかった主張は「未確認」のまま**とし、断定しない。
   - 確認できなかった・拒否された主張の扱いは、「記述の削除」「版と条件を明記した中立な表現への修正」
     「確認できた範囲だけに限定」のいずれかを提案する（比較の方針を変える提案ではなく、事実性の確保のため）。
   許可が得られない、または要確認の主張が無い場合は、この手順を飛ばしてその旨を報告に書く。

5. **報告**
   統合した指摘を、場所／内容／根拠／確信度／重要度／英語の修正案が分かる形で提示する。
   他パッケージ言及の一覧（場所・パッケージ・分類・確認状況）も付ける。
   指摘が無ければ「今回は指摘なし」と明示する。ドキュメントはこのスキルでは直さず、
   修正してよい指摘を選んでもらうよう案内する。

6. **起票（任意）**
   ユーザーが起票を希望した指摘について、`.claude/skills/refactor-candidates/SKILL.md`の手順4〜6
   （既存Issueとの照合 → 起票方針（対象・まとめ方・新規か追記か）の確認 → 最終案の確認 → 起票）に従う。
   関連する指摘は1つのIssueにまとめるのが基本（5章）。本文は**英語**。
   「挙動に関わる指摘」を起票するか会話内の報告に留めるかも、その場で確認する。
   ユーザーの合意なしにIssueを作成・コメントしない。

## 完了条件

- 対象の全ページについて、2つのエージェントの結果を統合して提示している（指摘なしも明示）
- 要Web確認の主張について、ユーザーの許可を得て確認した、または確認していないことを明示している
- 起票を希望された場合は、合意どおりに起票してIssue番号またはURLを報告している

## 制約

- ドキュメント・コード・設定ファイルを変更しない。
- Web検索は、検索する主張と検索語を示してユーザーの許可を得てからにする。
- 他パッケージについて、確認していないことを根拠に「誤り」「劣る」と書く修正案を出さない。
- 指摘・修正案に、`docs/spec/`・`.claude/`・`CLAUDE.md`への参照や、Issue番号を書かない
  （公開側は英語で、内部文書を指さない。6章・13章）。
