## 踏んだ罠（再発防止）

- **`Estimator::fit()` 冒頭で `crate::shared::parallelism::ensure_serial()` を呼ぶ**: faer のグローバル並列度を `Par::Seq` に固定する。理由・背景の詳細は `engine/src/linear/CLAUDE.md`「faerのグローバル並列度」と `.claude/rules/rust-style.md`「パフォーマンス」節を参照（tall-skinny な設計行列での暗黙全コア並列化が多コア機・負荷下で 20〜200倍遅く不安定になる）。`two_sls/fit.rs`/`gmm/fit.rs` の各 `fit()` に追加済み（第一段階・第二段階の `OlsEstimator::fit` 側でも二重に呼ばれるが冪等なので無害）。**新しい IV 系手法の `fit()` を足したら忘れないこと**。回帰ガードは各 `fit()` の `fit_pins_faer_global_parallelism_to_seq`（`two_sls/fit/tests/basic.rs`）。
- **`cov_type=Cluster`のクラスター数`G`と構造方程式の傾き係数の数`q`の関係（`G <= q`は`ValidationError`）**: `two_sls/fit.rs`/`gmm/fit.rs`ともに、クラスターロバストな係数共分散`Ŝ`はクラスター寄与スコアの総和がゼロ（正規方程式`X'e = 0`）で`rank(Ŝ) ≤ G - 1`のため、ロバストWald/F（χ²）検定の`q×q`部分行列が`G <= q`で構造的に特異になる（`engine/src/linear/CLAUDE.md`「クラスター数`G`と傾き係数の数`q`の関係」と同じ構造）。`fit()`冒頭で構造方程式の`q = k - k_constant`を使って`CommonError::InsufficientClustersForInference`（`ValidationError`）で弾く（判定は`common/validation.rs`の`validate_structural_cluster_count`に集約し、`validate_iv_fit_inputs`経由で`two_sls/fit.rs`/`gmm/fit.rs`/`engine_pybind`が共有する。`q`の式を複製しない）——第二段階回帰の`OlsEstimator::fit`内でも同じ検証が走るが、そちらは`SecondStageFailed`にラップされるため、`fit()`冒頭で構造方程式の`q`を使って一貫させる（`fit_returns_validation_error_when_cluster_count_at_most_slopes`で固定）。`engine_pybind::fit()`も`compute_first_stage`より前に同じ検証（`validate_iv_fit_inputs`）を呼ぶ（そうしないと第一段階が先に発火してこのチェックにPythonから到達できない）。構造方程式では`G>q`でも第一段階の`q`（`q_first >= q_struct`）が`G`以下のときは、`compute_first_stage`が第一段階を`OlsEstimator::fit_with_optional_f_test`で推定するため`FirstStageFailed`にはならず、その第一段階の全体F検定（`f_statistic()`/`f_p_value()`/`f_df()`）だけが`None`になる（係数・標準誤差・弱操作変数診断は有効。構造方程式は全体Wald検定が必須の出力なので拒否のまま、第一段階は診断なので`None`、という線引き。`G<2`・`groups`未指定は従来どおり`FirstStageFailed`。境界は`compute_first_stage_leaves_overall_f_undefined_when_g_equals_first_stage_slopes`/`compute_first_stage_computes_overall_f_when_g_exceeds_first_stage_slopes`と`tests/iv/test_iv_validation.py`の`test_cluster_count_boundaries`で固定）。第二段階の`OlsEstimator::fit`は従来どおり`SecondStageFailed`にラップされる。Wu-Hausman拡張回帰は残差列の分だけ`q_aug = q + k_endog`が増えるため`G <= q_aug`で拡張回帰の`OlsEstimator::fit`が`InsufficientClustersForInference`を返しうるが、Wu-Hausmanが実際に使うのは末尾`k_endog`列の`k_endog×k_endog`部分行列（`rank(Ŝ) ≤ G-1 ≥ k_endog`なら計算可能）なので、他のdegrade理由と同じく`wu_hausman_*`を`None`へdegradeする。
- **観測数`n`は`validate_observation_counts`（`common/validation.rs`）で、構造方程式の`n <= k`（`CommonError::InsufficientObservations`）→第一段階の`n <= l`（`IvError::InsufficientObservationsForFirstStage`）の順に`fit()`冒頭で検証する**（`l = k_exog + k_instruments`、定数項込み。`validate_iv_fit_inputs`経由で`TwoSlsEstimator::fit`/`GmmEstimator::fit`/`engine_pybind`が共有し、`k`・`l`の式を複製しない）。`n <= l`は第一段階を診断としてdegradeできない: `n == l`で`Z`が正則になり第一段階が完全に当てはまって`X̂ = X`（2SLSはOLSと係数が一致、GMMも`W₀ = (Z'Z)⁻¹`でOLSに縮退）、`n < l`で`Z'Z`が特異、弱操作変数Fの残差自由度`n - l`も0以下になる。クラスター数の`G <= q_first`が全体F検定だけを`None`にできる（`wald`の`q×q`部分行列に固有の問題）のとは性質が違う。`l >= k`（識別の順序条件）なので`n <= l`は`n <= k`を含み、構造方程式を先に報告しないと第一段階の`k`に隠れる。`GmmEstimator::fit`も`n == l`でOLSに縮退して成功してしまうため、`Z'Z`の数値的な特異の検出任せにせずこの共通検証で弾く。境界は`validate_observation_counts_*`（`common/validation.rs`）・`fit_returns_insufficient_observations_for_first_stage_when_n_is_at_most_l`（`two_sls/fit/tests/validation.rs`/`gmm/fit/tests/validation.rs`）で固定。
- **`gmm_weight_type=Cluster`のクラスター数`G`と操作変数の数`l`（全操作変数`x_exog ++ instruments`の列数）の関係（`G<l`で構造的に特異）**: `gmm/weight.rs`の`WeightType::Cluster`（モーメント条件の分散共分散行列`S`、l×l）は`S`がG個のランク1行列の和なので`rank(S)≤G`であり、`G<l`だと`S`が必然的に特異になる（実装中に2グループ・3操作変数のテストケースで実際に踏んだ。行列計算に入る前に下記のバリデーションで弾く）。**これは上記`cov_type=Cluster`の`G <= q`とは別軸（対象が係数共分散ではなくモーメント重み行列、閾値も`q`ではなく`l`）のため、`CommonError`ではなくGMM専用の`IvError::InsufficientClustersForWeightMatrix { g, l, min_clusters }`（`ValidationError`）として`validate_weight_type`（`TwoStep`/`Iterated`で検証。`OneStep`は`weight_type`を持たないため対象外）で弾く。閾値は識別状態で異なる**: 過剰識別（`l > k`）は`Z'ê=0`が成り立たず`rank(S)≤G`なので`G < l`、丁度識別（`l == k`）は`Z'ê=0`（`Σ_g S_g=0`）により`rank(S)≤G-1`なので`G <= l`（実測で確認: 丁度識別の`G==l`を弾かないと計算エラーになる）。過剰識別の`G==l`は成功する。数値的な特異（`NearSingularMatrix`）は悪条件のbackstopとして残る（`fit_returns_insufficient_clusters_for_weight_matrix_*`/`fit_succeeds_when_*_g_equals_l`/`fit_succeeds_when_just_identified_and_g_exceeds_l`で固定）。 クラスター系の境界値テストを書くときは、常に「G ≥ 対象の分散共分散行列の次元」を確認する。
- **第一段階の`OlsInput::from_columns`には、焼き込み済みの定数項列を取り除いた「素の」`x_exog`と`include_intercept=input.has_intercept()`を渡す**（`common/input.rs`の`without_baked_in_intercept`）。`IvInput::x_exog()`は`include_intercept=true`のとき先頭に定数項列（"const"）を既に含む。`OlsInput.has_intercept`は「切片列を追加するか」と「`k_constant`（統計量計算で切片を除外する基準）」の**両方**を兼ねるため、二重切片を避けようとして`false`を渡すと`k_constant`が`0`になり、`k_constant`に依存する統計量が誤る。

- **クラスター列は`CovType::Cluster`/`WeightType::Cluster`が整数コード（`GroupCodes`、`shared/group_codes.rs`）で受け取り、検証・集計・第一段階・Wu-Hausman拡張回帰で同じコードを使う**: コード化は`engine_pybind`（`extract_cluster_groups`）が渡す時点で一度だけ行い、engineの`fit()`はコードをそのまま借りる（`String`列を受け取って`fit()`内でコード化し直す、ということはしない）。`common/validation.rs`の`validate_structural_cluster_count`が構造方程式のクラスター数検証（`G>=2`・`G>q`。`validate_iv_fit_inputs`の一部として`engine_pybind`も使う）。第一段階は`compute_first_stage`が`cov_type.clone()`ごと`OlsEstimator::fit_with_optional_f_test`に渡す（コードのコピーは`n`個の`usize`で、`String`列のコピーより軽い。ただし第一段階の推定量は`cov_type`ごとコードを結果の寿命まで保持するため、内生変数の数だけ`n`個の`usize`が常駐する。n=1,000,000で1変数あたり約8MB。`GroupCodes`を`Arc`で共有すればなくせるが、効果が小さいため見送っている）。`gmm/weight.rs`の`validate_weight_type`は`weight_type=Cluster`のグループ（コード）を返し、そのコードを反復の間そのまま借りて`cluster_moment_covariance`に渡す（`cluster_meat`は行インデックスを作らず行を1回走査するため、反復GMMでも事前の構築は要らない）。**`cov_type`と`weight_type`のコードは、同じ列名を指していても別々に渡される別物**（`engine_pybind`は`cov_type`と`weight_type`でそれぞれ`extract_cluster_groups`を呼ぶ）。
- **GMMの重み行列`S`はスカラー倍で点推定`β̂`が変わらない**: `β̂(W) = (X'ZWZ'X)⁻¹X'ZWZ'y`で`W=S⁻¹`のため、`S`を正の定数`c`倍すると`W`が`1/c`倍され、分子・分母両方に乗って相殺する（`gmm/iterate.rs`の`gmm_point_estimate_is_invariant_to_positive_scaling_of_s`で検証済み）。そのため`gmm/weight.rs`の`robust_moment_covariance`/`cluster_moment_covariance`/`kernel_moment_covariance`は、`two_sls/cov.rs`の対応する`hc_cov_params`/`hac_cov_params`・共有の`cluster_cov_params`が持つ小標本補正（HC1の`n/(n-k)`、クラスターの`(G/(G-1))((n-1)/(n-k))`）を意図的に適用していない（これらは全成分に一律に乗るスカラーのため）。ただしHC2/HC3のレバレッジ補正は成分ごとに異なる重みのため、この理屈は適用できない（GMMの`gmm_weight_type`にHC2/HC3相当の区分が無いのはこのため、`docs/spec/iv-spec.md`1.2節）。
- **GMMの推定方式は`GmmType`のenum（`OneStep`/`TwoStep{weight}`/`Iterated{weight,max_iter,tol}`）で選ぶ（回数の整数`gmm_iterations`は廃止）**: 標準的なGMM文献（Hansen 1982、Hayashi、Wooldridge）・`docs/spec/iv-spec.md`3.3節の用語法では、「1-step GMM」は残差に基づく重みの再構築を一切行わずアドホックな`W₀=(Z'Z)⁻¹`のみで打ち切る推定（常に2SLSと同じ結果）、「2-step efficient GMM」が「初期推定→残差からS構築→S⁻¹で再推定」という2段階手続きを指す。回数の整数で方式を表すと「2が2段階GMM」という対応を知らないと読めず、許容誤差の有無で意味が切り替わっていたため、矛盾した組み合わせ（1段階に反復設定、1段階に`weight_type`等）を型で表現できないenumにした。
- **3種の方式は1つのループで統一できる**: `gmm/iterate.rs`の`gmm_iterate`（`fit()`が呼ぶ）は「直前の残差からSを再構築→再推定」という1ステップを`while`ループで最大推定回数（`OneStep`=1、`TwoStep`=2、`Iterated`=`max_iter`）に達するまで繰り返すだけで、方式ごとにアルゴリズムを分岐させない（`OneStep`は`weight_type`を持たないためループ自体に入らない）。Python API層の`estimator`（`"2sls"`/`"gmm"`）は確立済みの設計で、方式はGMMという1つのestimatorのパラメータ`gmm_type`として扱う。
- **収束条件（`gmm_tol`）は係数のelementwise・絶対誤差＋相対誤差併用で判定する**: `gmm_coefficients_converged`（`gmm/iterate.rs`）が`tests`の数値クロスチェックと同じ`tol = max(rtol * |ref|, atol)`（`ref`は直前の係数）を各係数について判定し、全係数が満たして初めて収束とする（ベクトルノルムの比ではなくelementwise maxを取る設計、1つでも収束していない係数を見逃さないため）。`atol`（`GMM_CONVERGENCE_ATOL=1e-8`）はユーザーに公開せず内部固定値とする——`gmm_tol`という単一パラメータで「rtol相当」を指定させる設計にしたため（atol/rtolを別々に公開する案もあったが、`nonlinear`の`tol`（単一の勾配ノルム閾値）と同じ「単一ノブ」のシンプルさを優先）。
- **未収束時の挙動は`nonlinear::common::run_solver`の`max_iter`/`tol`/`raise_on_non_convergence`/`converged`と同じ設計に揃えた**: `Iterated`の`max_iter`は収束判定の上限（初回推定を含めて数える、linearmodelsの`iter_limit`と同じ。3以上必須で、2以下は`TwoStep`に収束判定を付けただけになり紛らわしいため`InvalidGmmMaxIter`）。理論上は収束するはずでも実務データでは収束しないケースがありうるため、上限は必須という判断。`raise_on_non_convergence=true`（既定）なら`IvError::GmmNonConvergence`、`false`なら`converged=false`のまま結果を返す（MLEの`raise_on_non_convergence=false`→`converged=False`と同じ意味論）。
- **`OneStep`/`TwoStep`は収束判定を行わず常に`converged=true`、`n_iter`は実際の推定回数（1・2）**: 収束判定は2つの推定値（前回・今回）を比較して初めて意味を持ち、`Iterated`は`max_iter>=3`のため比較対象が必ず存在する。`OneStep`/`TwoStep`で「収束しなかった」とエラーにするのは意味不明なため、判定自体を持たない（`fit_treats_two_step_as_always_converged`で固定）。`estimator="2sls"`の`n_iter=1`とも整合する。
- **`OneStep`は`weight_type`を持たず検証もしない。`TwoStep`/`Iterated`は`validate_weight_type`で`fit()`冒頭に検証する**: 方式ごとに使う設定だけを持つenumにして「使わないものは受け取らない」形にしたため、`OneStep`に対する`weight_type`の検証は不要。`TwoStep`側は`validate_weight_type`と`fit()`本体の`match`（`S`構築の過程）で同じチェックを重ねて行う（意図的な二重チェック、コストは軽微）。

- **弱操作変数診断（部分F統計量）は常に等分散前提、`cov_type`には依存しない**: `common/first_stage.rs`の`partial_f_statistic`（`x_endog[j] ~ x_exog + instruments`と`x_endog[j] ~ x_exog`のSSRを比較する古典的ネストF検定）は、呼び出し元が`fit()`に指定した`cov_type`によらず常にこの計算方式を使う。理由は2つ: (1) Stock-Yogoの臨界値表自体が等分散前提でキャリブレーションされている（v1では臨界値照合はしないが意味合いは引き継ぐ）、(2) `OlsEstimator`は`cov_params()`を持つが、それは第一段階で指定した`cov_type`の行列であり、制限モデルとの比較に使う`cov_type`対応のロバスト部分Wald検定には別途拡張が必要なため、常に等分散前提とする。他の診断的統計量（Sargan/Hansen J・Wu-Hausman等）を実装する際も、「`cov_type`を反映すべきか、常に固定の計算方式でよいか」は自明ではないため都度確認する。
- **`x_exog=[]`かつ`include_intercept=false`（制限モデルに回帰変数が1つも無い）の退化ケース**: `partial_f_statistic`の制限モデル（`x_endog[j] ~ x_exog`のみ、`instruments`を除く）が回帰変数0個になりうる。`OlsEstimator`は0列の設計行列を受け付けない（`CommonError::NoRegressors`）ため、この場合はSSR_rを`y_endog`自体の二乗和として直接計算する特別扱いが必要（`fit_computes_weak_instrument_f_statistic_when_x_exog_is_empty_and_no_intercept`で固定）。同様に「モデルの一部の変数を除いた退化ケース」を扱う他の診断統計量でも、退化した制限モデルが0変数になりうるケースを見落とさないこと。
- **制限モデルの設計行列は、full column rank検証済みの制限なしモデルの列部分集合であれば必然的にfull column rank**（線形代数の一般的性質: full column rankな行列の列の任意の部分集合も線形独立）。`partial_f_statistic`はこれを根拠に、制限モデルの`OlsEstimator::fit`が`SingularMatrix`等で失敗することを理論上不可能と扱い、`?`で防御的に伝播するだけに留めている（`xtx_inverse`と同じ「理論上到達不能だが`Result`で扱う」パターン）。ネストモデル比較（尤度比検定等）を今後実装する際、同じ議論が使える。

- **Wu-Hausman検定（回帰ベース）は`fit()`に渡された`cov_type`に対応させる**（弱操作変数診断とは対照的な判断）: `two_sls/wu_hausman.rs`の`wu_hausman_test`（`fit()`が呼ぶ）が構造式（`y ~ x_exog + x_endog`）に第一段階残差を追加回帰し（`linearmodels`の`wooldridge_regression`相当）、追加した残差係数のジョイントWald検定を`cov_type`と同じ設定で行う。理由は、（当時参照した）`linearmodels`の`wooldridge_regression`のdocstringが「fit時と同じcovarianceでのWald検定」という仕様であるため（部分F統計量とは異なりStock-Yogo等の等分散前提のキャリブレーションに縛られない）。この対応のために`OlsEstimator::wald_test_last_columns`（`engine/src/linear/CLAUDE.md`参照）を新設した。他の診断的統計量（Sargan/Hansen J等）を実装する際も、都度どちらが適切か確認する（弱操作変数診断の教訓と同じ）。
- **Wu-Hausmanの拡張回帰が想定内の理由で失敗した場合は`fit()`全体を失敗させず、`wu_hausman_statistic`/`wu_hausman_p_value`だけ`None`にする**（`FirstStageFailed`/`SecondStageFailed`の"all-or-nothing"方針とは意図的に異なる）: 想定内の理由は2つ（`PerfectFit`・`SingularMatrix`・`InsufficientObservations`等の失敗を含む）。(1) 拡張回帰が完全フィットで`PerfectFit`になる（第一段階残差の分散がゼロ＝操作変数が内生変数を完全予測する退化ケースは、第一段階が先に`PerfectFit`で止める）、または設計行列が特異（`SingularMatrix`）になる。(2) 拡張回帰は第二段階より内生変数の数だけ列が多い（`k_exog+2*k_endog`列、残差列が追加分）ため、境界的なサンプルサイズでは第二段階は成功するが拡張回帰は`InsufficientObservations`になりうる。`params`/`std_errors`等の主要な推定結果はWu-Hausman計算と無関係に正しく計算できるため、診断統計量1つの失敗で`fit()`全体を巻き込まない（`x_endog=[]`のときの`None`と同じ意味論に統合）。**それ以外の失敗（`CommonError::NearSingularMatrix`——Wald検定側の数値的なほぼ特異性——を含めた上記3種類以外）は`None`へ握りつぶさず`IvError::HausmanRegressionFailed`として伝播する**（広すぎる`Err(_)`キャッチは将来の実装バグを`None`で隠してしまうため、`two_sls/wu_hausman.rs`の`match`で3バリアントだけを明示的に拾う）。実装は`OlsInput::from_columns`→`OlsEstimator::fit`→`wald_test_last_columns`をクロージャで包み`Result`を得てから`match`で明示的に振り分ける形（`?`を使う既存のall-or-nothing系エラー伝播とは書き方が異なる点に注意）。他の診断統計量でも「失敗時にfit()全体を道連れにすべきか、その統計量だけNoneにすべきか」・「Noneにする失敗理由をどこまで広げるか」は自明ではないため都度確認する。

- **過剰識別検定（Sargan/Hansen J）の`cov_type`/`gmm_weight_type`依存性は、弱操作変数診断・Wu-Hausmanとは異なり都度確認不要だった**: Sargan検定（`two_sls/sargan.rs`）は定義自体が等分散前提の検定であり、不均一分散に頑健な版が欲しい場合はGMM＋Hansen J検定を使うのが標準的な使い分けのため、常に古典的（`e'Z(Z'Z)⁻¹Z'e/σ̂²`、`σ̂²=e'e/n`）な計算式を使い`cov_type`には依存しない。Hansen J検定（`gmm/hansen_j.rs`）は逆に、点推定に使った重み行列`S`（`gmm_weight_type`依存）をそのまま流用するのが定義そのもの（`J=(Z'ê)'S⁻¹(Z'ê)`）であり、これも判断の余地がない。両者とも自由度は`len(instruments) - len(x_endog)`（Sargan検定と同じ、`two_sls/sargan.rs`の`sargan_test`参照）で、丁度識別（自由度0）なら`None`（`docs/spec/iv-spec.md`3.5節）。
- **Hansen J統計量は`n`で割ってはいけない**: `gmm/weight.rs`が構築する`S`（本ファイル「`gmm_weight_type`ごとの`S`」参照）は`n`で正規化していない生の和`S=Σᵢêᵢ²zᵢzᵢ'`のため、標準形`J=n·ḡₙ'Ŝ⁻¹ḡₙ`（`Ŝ`は正規化済み、`ḡₙ=(1/n)Z'ê`）に代入すると`n`は完全に相殺し`J=(Z'ê)'S⁻¹(Z'ê)`になる。`quad/n`とすると統計量が常に`1/n`倍に過小評価され、過剰識別検定が実質機能しなくなる（サンプルサイズが大きいほど深刻）。オラクル側にも同じ`/n`を複製する自己参照的な検証では検出できない。**他の統計量で「`S`が`n`で正規化済みかどうか」を暗黙の前提にする実装をする際は、この教訓（正規化の有無を数式の途中で見失うと`n`のオーダーで結果がズレる）を踏まえ、自己参照的でない検証手段（後述のSargan比較等）を必ず用意する。**
- **Hansen Jの`OneStep`（1-step GMM）時、および`gmm_weight_type=Classical`時の`S`は`σ̂²・Z'Z`（`σ̂²`スケーリング必須）**: 点推定は正のスカラー倍不変のため`S=Z'Z`のままでも`β̂`は変わらないが、Hansen Jは絶対スケールに依存するため`Robust`/`Cluster`/`Hac`と同じ「`S=n・Ŝ`」の関係を満たすには`Ŝ_homoskedastic=σ̂²・(1/n)Z'Z`から`S=σ̂²・Z'Z`が必要。`σ̂²`はstep-0残差`ê₀=y-Xβ̂₀`から`σ̂²₀=ê₀'ê₀/n`で計算する（`OneStep`ではstep-0残差＝最終残差のため同じ値が使える）。この修正により`gmm_weight_type=Classical`かつ`TwoStep`のHansen Jは`two_sls/sargan.rs`のSargan統計量と数値的に一致する（`gmm/hansen_j.rs`の`fit_computes_hansen_j_statistic_matching_two_sls_sargan_when_weight_type_is_classical`で検証、点推定側の`fit_matches_two_sls_point_estimate_when_weight_type_is_classical`と対になる不変条件チェック）。1-step GMM（`S₀=Z'Z`）でも同じ理由で`σ̂²₀`スケーリングが必要。
- **Sargan/Hansen Jの計算失敗はWu-Hausmanと異なり`None`にせず`IvError`として伝播する**: 両者が使う`Z'Z`（Sargan）・`S`（Hansen J）は、いずれも`fit()`の主要な点推定計算（第一段階回帰・`gmm_point_estimate`）で既に反転成功済みの行列の再利用（`σ̂²・Z'Z`は正定値行列の正のスカラー倍のため同じく正定値）であり、理論上ここでの特異性は到達不能（`two_sls/cov.rs`の`xtx_inverse`と同じ防御的`Result`化）。Wu-Hausmanのように新規に組み立てる設計行列（拡張回帰、分散ゼロ列が混入しうる）とは性質が異なるため、「想定内の理由で失敗しうるからNoneにする」という判断はそもそも当てはまらない。

- **`cov_type=Hac`のテストは`lags=None`（経験則自動計算）・`lags=Some(正の値)`（Newey-Westの重み付けループ本体）・`time_order=Some(...)`（時系列順の並べ替え）の3種を揃える**: `lags=Some(0)`（HC0と一致する退化ケース）とエラーパスだけでは重み付けループ本体が通らず、`cargo llvm-cov`の%だけでは気づきにくい（`.claude/rules/rust-style.md`「テスト」節参照）。`two_sls/cov/tests/hac.rs`は`manual_hac_std_errors`（`hac_cov_params`の`matmul`実装とは別に素朴な二重ループで独立計算、`manual_hc_std_errors_with_weight`と同じ方針）で3種を検証する。
  - **`gmm/weight.rs`の`gmm_weight_type=Hac`**: `lags=Some(正の値)`のBartlettカーネル重み付けループ本体は`gmm/weight/tests/robust_hac.rs`の`fit_computes_hac_weighted_estimate_matching_manual_formula_with_lags_two`が独立手計算のオラクルと照合し、`lags=None`（自動計算）・`time_order=Some(...)`は`fit_with_hac_weight_type_and_auto_lags_matches_explicit_lags_two`・`fit_with_hac_weight_type_respects_time_order`が固定する。他の手法でHAC/カーネル型の重み付けを実装する際は、`lags=Some(正の値)`のループ本体・`lags=None`・`time_order`の3種を最初からセットで用意し、どれが既にカバー済みかをこの種の思い込みで判断せず`cargo llvm-cov`の欠落行を実際に確認すること。
- **推定量構造体の単純なgetter（`dep_var_name()`・`nobs()`・`k()`等）は、実際に計算結果として公開している値でも、テストが一度も呼び出していないと`cargo llvm-cov`で未カバーになる**（`gmm.rs`の`GmmEstimator`・`two_sls`の`TwoSlsEstimator`双方で発覚）。既存の値検証テスト（`fit_matches_...`等）は`params()`/`std_errors()`等の主要な値しか読まないことが多く、他のgetterを素通りしやすい。`two_sls/fit/tests/basic.rs`の`fit_succeeds_when_over_identified`（`nobs`/`k`/`dep_var_name`をまとめて確認）のような「基本メタデータgetter群」テストを1つ用意し、新しいgetterを追加するたびにそこに追記する運用にすると見落としにくい。

- **`linearmodels`とのベンチマーク照合で判明した対応関係は`benchmark/iv/references/linearmodels_ref.py`のモジュールdocstringが正本**: `cov_type`↔`linearmodels`の`cov_type`/`debiased`の対応表、`debiased`が推論統計量の分布（t/F vs z/カイ二乗）を切り替える仕様、`wu_hausman_statistic`の照合には`res.wu_hausman()`ではなく`res.wooldridge_regression`（モデルの`cov_type`をそのまま使うaugmented regression）を使う必要があること（`hac`を含む全`cov_type`で一致。`hac`は`debiased=False`で`fit`する）等。`/test-new`でIVのpytestを書く際・GMMの`cov_type`対応を実装する際は、まずこのdocstringを確認してから再調査する（`docs/spec/iv-spec.md`3.1節・3.2節にも要点を反映済み）。
- **`wu_hausman_p_value`のF分布p値は、augmented regression（第一段階残差をn_endog列追加した拡張回帰）自身の`df_resid`（＝主構造式の`df_resid - n_endog`）を使う**（`OlsEstimator::wald_test_last_columns`が内部で使う`df_inference`と同じ、`engine/src/linear/CLAUDE.md`参照）。統計量自体（`wr_stat`）は主モデルのdfに依存しないため、この分母dfを取り違えても機械精度で一致してしまい見逃しやすい——主構造式の`df_resid`を流用すると`wu_hausman_statistic`は機械精度で一致するのに`wu_hausman_p_value`だけ最大0.2%程度（small_nシナリオ、df=37と36の違い）乖離する。統計量とp値は別々に照合すること（`tests/iv/test_iv_reference.py`、`benchmark/iv/references/linearmodels_ref.py`）。

- **被説明変数の定数・完全フィットの判定位置**: 構造方程式の定数（`validate_outcome_not_constant`、切片あり・`y`が全行等しい）は`TwoSlsEstimator::fit`/`GmmEstimator::fit`/`engine_pybind`の`fit`が第一段階より前に呼ぶ。完全フィットは**構造残差**$y - X\hat\beta$で判定する（2SLSは`ssr`の直後、共分散より前。GMMは初期推定の残差で、重み行列`S`が0になって逆行列が特異になる前）。第二段階の`OlsEstimator`は`X̂`への回帰で別の量なので`fit_auxiliary`を使う。第一段階は`fit_with_optional_f_test`（判定あり）なので、操作変数が内生変数を完全に予測すると`FirstStageFailed`で`PERFECT_FIT`（`stage=FIRST_STAGE`）になる——Wu-Hausman拡張回帰は元の`y`の回帰なので`fit`（判定あり）で行い、拡張回帰が完全フィット（`y`が第二段階の説明変数と第一段階残差で厳密に説明される。第一段階も構造残差も完全フィットではないので前段の判定をすり抜ける）なら`PerfectFit`を他の想定内の失敗と同じく`None`へdegradeする（`wu_hausman_statistic`が`8e31`・p値0のような無意味な値で成功するのを防ぐ）。第一段階残差の分散がゼロによる特異は第一段階の判定で先に止まるため通常は到達しない（`SingularMatrix`の`None`への分岐は防御として残す）。部分F統計量の制限モデルは`fit_auxiliary`。テストで操作変数が内生変数を完全に予測するデータ（`x_endog = z`等）を使うと第一段階が失敗する。

## 2SLSとGMMの独立実装方針

- `TwoSlsEstimator`（`two_sls.rs`）と`GmmEstimator`（`gmm.rs`）は、点推定の意味では`gmm_weight_type=Classical`のGMMコアが2SLSと数値的に一致する（`gmm/fit/tests/basic.rs`の`fit_matches_two_sls_point_estimate_when_weight_type_is_classical`で検証済み）が、実装は意図的に独立させている（`TwoSlsEstimator`は`cov_type`対応の推論統計量一式を持つのに対し`GmmEstimator`は点推定のみのスコープで持たないため、委譲すると過剰設計になる。詳細な理由は`gmm.rs`冒頭のdocコメント「2SLSとの共通化の判断」参照）。
- `fit()`は段階ごとの非公開関数を順に呼ぶ構成（2SLS: `covariance_stage`（`df_resid`を引数で受け取る）・`wu_hausman_test`・`sargan_test`、GMM: `gmm_iterate`・`hansen_j_test`・`sandwich_covariance`）。`Mat`の横連結`hcat`と`fit()`冒頭の検証`validate_iv_fit_inputs`は`common/`に置いて2SLS・GMMが共有する。推定結果の共通の読み出し口（係数・標準誤差・検定・適合度など約20個）は`common/estimate.rs`の`IvEstimate`traitで、2SLS・GMMが実装する（`engine_pybind`が`IVResult`の共通フィールドを一度だけ詰めるための口。共通フィールドを足すとどちらかの実装漏れがビルドエラーになる）。推定量ごとに意味や型が違うもの（`sargan_*`・`hansen_j_*`・`wu_hausman_*`・`wald_df`・GMMの`n_iter`/`converged`等）は`IvEstimate`に入れず、各推定量のメソッドとして持つ。traitの範囲を広げるのは3つ目の推定量（FeIv等）が出てからにする。推論表（標準誤差・統計量・p値・信頼区間）の`inference_table`は`shared/inference.rs`に置いてFE・RE・2SLS・GMMが共有する（検定統計量の分布だけが違うため、分布を引数に取る）。
- 同じ理由で、`gmm/weight.rs`のモーメント共分散行列計算（`robust_moment_covariance`等）は`two_sls/cov.rs`のサンドイッチ型分散計算（`hc_cov_params`等）と数式上ほぼ同型だが、コードは共有せず独立に実装している。**例外はクラスターの蓄積`Σ_g S_g S_g'`と小標本補正、およびHACのラグ数の解決（`shared::covariance::resolve_hac_lags`。検証・既定式とも1か所）**で、`shared::covariance`の`cluster_meat`/`cluster_correction`を2SLS・GMM・OLS・panel・nonlinearが共有する（加算順を1か所に固定し、最適化も1か所で行うため。2SLSのクラスター共分散は共有の`cluster_cov_params`を`X̂`・構造残差`e`で呼ぶ。GMMの`cluster_moment_covariance`も`cluster_meat`を使う）（`docs/spec/iv-spec.md`3.1節の「IVのサンドイッチ型分散計算はOLS/nonlinearに寄せず独立実装でよい」という既存方針を、2SLS/GMM間の関係にも適用した判断）。
- **GMMの`cov_type`対応（`docs/spec/iv-spec.md`3.1節）**（`gmm.rs`のモジュールdocコメント「標準誤差・検定統計量（cov_type対応）」参照）。
- **GMMのSEサンドイッチは常に一般形を使う**（`Avar(β̂) = B⁻¹(X'ZWΩ̂WZ'X)B⁻¹`、`B=X'ZWZ'X`、`W=S_used⁻¹`は点推定に実際に使った重み）: `gmm_weight_type`と`cov_type`は独立な選択（本ファイル前段の設計と同じ）のため一般に一致せず、「効率的GMM」の特殊ケース（`gmm_weight_type`相当が`cov_type`と一致）でも`B⁻¹`のみへの簡略化分岐はしない（実装が単一経路になり単純）。`S_used`が`OneStep`のとき実際の点推定に使われた`Z'Z`ではなく`unadjusted_s`（`σ̂²₀・Z'Z`）であっても、サンドイッチ全体のスケール不変性（`B→cB`なら`B⁻¹→B⁻¹/c`、`meat→c²・meat`で相殺）により`cov_params`は変わらない——`fit_computes_hc1_std_errors_matching_manual_formula_with_one_step_gmm`で実測確認済み。
- **GMMの`cov_type=Classical`は残差を中心化してσ̂²を計算する**: `σ̂² = Σ(êᵢ-ē)²/df_resid`（非中心化SSR`Σêᵢ²/df_resid`ではない）。2SLS/OLSは正規方程式により定数項を含む限り常に`ē=0`が成り立つため中心化の有無で結果が変わらないが、GMMの一次条件`X'ZWZ'ê=0`は`gmm_weight_type=Classical`（2SLSと同じ点推定になる特殊ケース）以外では`ē=0`を保証しない——`X'ZW`という重み付き制約であり、`ē=(1/n)Σêᵢ`という単純平均をゼロにする制約とは一般に一致しないため。`gmm_weight_type=Classical`では`ē≈0`で非中心化でも一致するため、`gmm_weight_type=Robust/Cluster/Hac`で初めて（最大0.003%程度）ずれる。`linearmodels`の`IVGMMCovariance`が呼ぶ`HomoskedasticWeightMatrix.weight_matrix`（`cov_type=Classical`相当）のソースを確認し、常に中心化する設計（"``center`` has no effect on this estimator since it is always centered."とdocstringに明記）であることと一致させている。**HC0-3/HAC/クラスターの`Ω̂`は影響を受けない**（`linearmodels`側の対応する`HeteroskedasticWeightMatrix`/`KernelWeightMatrix`/`OneWayClusteredWeightMatrix`は`center`が既定`False`で、非中心化がそもそも仕様通りのため）。手計算オラクルが実装と同じ非中心化SSRを複製すると検出できない（Hansen Jの`/n`・Wu-Hausmanのdf取り違えと同型の「自己参照的オラクルは実装と同じ間違いを複製する」パターン、`engine/src/linear/CLAUDE.md`参照）。GMMの`Ω̂`計算を拡張・変更する際は、`gmm_weight_type≠Classical`のケースで独立に（自己参照でなく）検証することを徹底する。
- **HC2/HC3の`Z`ベース自己拡張は「レバレッジの計算」にのみ妥当で、「小標本補正の分母」にまで機械的に適用するのは誤り**: `two_sls/cov.rs`のHC1補正`n/(n-k)`・クラスター補正`(G/(G-1))((n-1)/(n-k))`を「`X̂`→`Z`、`k`→`l`」と機械的に置換して`hc1_correction`・クラスターの`correction`の分母に`l`（全操作変数の数）を使うのは誤り。小標本補正が表す「消費した自由度」は、常に構造方程式の`k`個のパラメータ（`ê_i=y_i-x_i'β̂`は常にk次元のβ̂から計算される構造残差）についてのものであり、`l`（外積を取る操作変数の本数、過剰識別なら`l>k`）とは無関係。レバレッジ`h_ii=z_i'(Z'Z)⁻¹z_i`（`Z`空間内での「距離」）は`X`→`Z`の機械的置換で妥当だが、補正係数の分母にまで同じ置換を適用してはいけない。`gmm_hc_omega`/`gmm_cluster_omega`のdocコメント参照。**「`two_sls/cov.rs`のパターンをZ/lに機械的に置換する」という自己拡張を行う際は、置換対象が本当に`l`（操作変数の次元）に依存する量か、それとも`k`（構造パラメータの数）に依存する量かを個別に確認すること**——今回のように「外積を取る対象の次元」と「自由度として消費した数」を混同しやすい。
- **`GmmEstimator::fit`は`confidence_level`の`(0,1)`範囲チェックと、`validate_observation_counts`による観測数の検証（`n<=k`と`n<=l`の両方）を持つ**（`OlsEstimator::fit`/`TwoSlsEstimator::fit`と同じ`CommonError::InvalidConfidenceLevel`/`InsufficientObservations`。`n<=l`の理由は上の観測数の項）。HC1/cluster補正の分母は`l`ではなく`k`を使う設計のため、`l`固有のNaN/Infinityリスクは補正側には無い。反復系・SE計算を伴う手法を新設する際、「NaN/Infinityの静かな伝播を防ぐ検証がどの次元（k? l? 他?）に対して必要か」は自明ではないため、各除算・各逆行列計算が実際にどの次元に依存するかを個別に確認すること。

## property-basedテスト（`mod proptests`）

- ケース生成器・`IvCase`・`assert_approx_eq`は`common/proptest_support.rs`（`#[cfg(test)]`）に一本化し、`two_sls/fit/tests/proptests.rs`/`gmm/fit/tests/proptests.rs`が共有する（Logit/Probitのように手法ごとに重複定義しない。データ構造が同一のため）。
- `x_endog`は操作変数の正の重み付き和＋第一段階誤差で生成し、`prop_assume!(fit().is_ok())`を安全弁にする。丁度識別（`iv_case_strategy(true)`）と過剰識別（`false`）を生成器の引数で切り替える。
- **GMMで「操作変数`Z`の列をスケール／混合しても点推定は不変」を安易に期待しない**: 2-step GMMは重み行列が`Z`の変換に追従するため点推定は不変になるはずで（理論上の推論であり実測はしていない）、`Z`の列を定数倍するバグ注入は列順序不変性のプロパティでは検出されない可能性が高い。列順序不変性の検証にバグを注入するときは`x_columns`（`X`側）を狙う（実際にそうして失敗を確認した）。
- バグ注入は「`n > 50`のときだけ発現する変更」にすると、`n`が小さい既存の固定値テストでは検出できず、proptestだけが失敗することを確認できる（proptestのケースは`n=40..=80`）。注入で生成された`proptest-regressions/`は本物の失敗ではないためコミットしない。
