# テスト方針（tests/）

このファイルは `tests/` 配下で作業する際に自動的に読み込まれる。

## テストの分離

- `engine`の純粋ロジックの単体テストは、対象コードと同じファイル内の`#[cfg(test)] mod tests`に置く（`cargo test -p engine`）。`tests/engine_tests/`ディレクトリは現状未使用（理由は`.claude/rules/rust-style.md`「テスト」参照）。
- `tests/api_tests/`: リファレンス実装との答え合わせテスト（`pytest`）。

## リファレンス実装

既存の検証済みパッケージとの数値比較で、パラメータ推定値の正しさを検証する。統計量ごとに主リファレンスを決め、独立実装によるクロスチェックも行う。

- **statsmodels**（Python）: OLS系（classical/HC0-3/cluster/HAC、AIC/BIC/log-likelihood、ロバストWald検定まで一貫して対応）の**主リファレンス**。動作確認済み（`benchmark/<系統>/run_statsmodels_benchmark.py`）。
- **R（`lm` + `sandwich`/`lmtest`パッケージ）**: 独立実装によるクロスチェック用。statsmodelsと計算方法の慣習が異なる可能性がある（自由度補正の既定値等）ため、**新しい統計量・cov_typeを追加するたびに、まずstatsmodelsとRが一致することを確認してからフィクスチャを固定する**。両者が一致しない場合は、既定値の違いを疑って調査する。
  - **クロスチェックの対象は係数・標準誤差に限らない**。R²・調整済みR²・AIC・BIC・対数尤度・F統計量・F検定p値等、推定結果として公開する統計量は全て独立実装でもcrosscheckする。一部の統計量だけRクロスチェックを省略し主リファレンス（statsmodels）のみに頼ると、主リファレンス自体のバグやプロジェクト固有の実装差に気づけない。
  - 慣習差の実例: RのAIC()/BIC()標準関数は残差分散を推定パラメータ1個として追加でカウントする（k+1）が、statsmodels・本実装は回帰係数の数kのみを使う。この場合はR標準関数をそのまま使わず、本実装と同じ計算式（`-2*loglik + 2*k`等）で独立に計算した値と比較すること（Rの値をそのまま使うと定数分ずれた「見せかけの不一致」になる）。
- **pyfixest**（Python）: OLSの正確性検証には使わない。fixest（R）本体のソースを確認したところ、pyfixest（Python、v0.60.0時点）のHC2/HC3標準誤差はfixestの設計ではなく**pyfixest自身の実装バグ**（HC1用の`N/(N-k)`小標本補正をHC2/HC3にも誤って適用）により系統的に乖離することが判明したため。性能比較（実行時間・メモリ）でのみ使う。固定効果が絡むPhase4（FE/RE）以降での正確性検証における採否は、その時点のfixest/pyfixestのソースを個別に確認して判断する（本項の結論をOLS以外に自動的に適用しない）。

## テスト用データセット

各推定手法は、以下の観点で網羅的にテストする。**全てのオプションの組み合わせで、リファレンス実装と統計量が一致することを確認する**。

1. **合成データセット**（`benchmark/generate_synthetic_datasets.py`で生成し、`benchmark/freeze_datasets.py`で`tests/api_tests/fixtures/benchmarks/data/`にCSVとして固定したものを使用。フィクスチャ生成・pytest実行時ともにこのCSVを読み、ジェネレータを直接呼ばない）。以下のバリエーションを持たせる。
   - サンプル数が少ない
   - 分散が大きい
   - 不均一分散（heteroskedasticity）
   - 自己相関（autocorrelation）: 主にHAC実装の検証用。他のcov_typeでは一般的な頑健性確認以上の意味は持たない
   - ある程度の多重共線性
   - 完全な多重共線性（設計行列が特異になるケース）: **リファレンス実装との数値比較はしない**（多くのリファレンス実装は冗長な列を自動的に落として続行するため、本プロジェクトの「エラーで止める」方針と挙動が異なる）。想定した例外（`ComputationError`）が発生することのみを確認する。
   - **境界値・悪条件（ill-conditioned）**: 自由度がちょうど1（`n = k+1`）での成功パス、変数間のスケールが極端に異なる場合（例: 一部の変数が10⁶オーダー、別の変数が10⁻³オーダー）、特異ではないが条件数が非常に大きい設計行列（相関0.99超等）。数値計算ライブラリ（faer等）依存部分の将来のリグレッションを検知するために有効。
2. **実データセット**: Wooldridgeデータセット等の教科書的実データ。真の係数と比較できないため、リファレンス実装との一致のみで検証する。
3. **グループ/クラスター単位の分散推定（クラスターロバストSE等）を持つ手法**: 均等サイズの疑似グループだけでなく、不均衡なグループサイズ（例: `[2, 3, 5, 10, 30, 50]`のように偏らせる）、グループ数が境界値に近いケース（最小グループ数ちょうど、その外側の失敗パス）、実データでのグループ列も検証する。均等サイズの疑似グループのみのテストは、実務でバグが出やすい分布の偏りを見逃す。
   - **境界値ケースでは「クラスタ数G」と「傾き係数の数q」の関係に注意する**（OLSのIssue #100で判明）。クラスターロバスト共分散行列はG個のランク1行列の和のため`rank ≤ G`であり、ロバストWald検定（F統計量）が使う`q×q`の部分行列はG<qのとき構造的に特異になりうる。係数・標準誤差自体はGが2以上であれば計算できるが、F検定を含む`fit()`全体がG<qで失敗しうる。「クラスタ数境界の成功パス」を作る際はqをG以下に保つ（詳細は`docs/planning/specs/ols-implementation-notes.md`「クラスター標準誤差」参照）。この関係はクラスターロバストSEを持つ他の手法（WLS/IV等）にも同様に当てはまるため、実装時に確認すること。

## テストの3系統

1. **成功パス**: 数値比較（フィクスチャJSONとの一致、下記参照）
2. **`ValidationError`パス**: 入力起因のエラー（欠損値、列の重複、観測数不足、`confidence_level`範囲外等）。想定した例外クラスが発生することを確認する（数値比較はしない）
3. **`ComputationError`パス**: 計算過程で発覚する問題（完全な多重共線性等）。同じく例外クラスの発生のみを確認する

## ベンチマーク値のフィクスチャ化

- リファレンス実装（statsmodels/R）の実行結果は、CIで毎回再計算せず、**JSONファイルとして`tests/api_tests/fixtures/benchmarks/`にコミットし固定する**。ベンチマーク由来のフィクスチャを`fixtures/`直下ではなく`benchmarks/`サブディレクトリに分けているのは、他の目的のフィクスチャ（ベンチマーク比較以外でテストが読み込みたいデータ）と混在させないため。
- 理由: CIを軽く保つため（Rパッケージのインストールはビルドが重い）。またリファレンス実装側のバージョンアップで数値が変わり、意図せずテストが壊れることを防ぐため。
- フィクスチャの命名: 手法・シナリオ・cov_type等が分かる形にする（例: `ols.json`に、シナリオ×cov_typeをネストして持たせる。実例は`tests/api_tests/fixtures/benchmarks/ols.json`参照）。
- **フィクスチャを生成するスクリプトと、生成されたJSON自体は別の場所に置く**。生成スクリプトは`benchmark/<系統>/fixtures/generate_<手法名>_fixtures.py`（コード、`benchmark/`側で管理。系統ディレクトリ構成は`.claude/skills/reference-benchmark/SKILL.md`参照）、生成物は`tests/api_tests/fixtures/benchmarks/<手法名>.json`（データ、テスト側で管理）。
- **合成データセット自体も同様にCSVとしてtests側（`tests/api_tests/fixtures/benchmarks/data/`）に固定する**（`benchmark/freeze_datasets.py`で生成）。理由: ジェネレータ側のコードが将来変わっても、既に固定したフィクスチャJSONの期待値と無言で不整合にならないようにするため。
  - **Wooldridgeデータセットはこの固定化の対象外**とする（`wooldridge`パッケージ自体はMITライセンスだが、同梱される実データの著作権は原典の教科書側にある可能性があり、フィルタ後の部分集合であってもMITライセンスの本リポジトリにCSVとして再配布してよいか未確認のため。ユーザー確認済み）。Wooldridgeデータは引き続き`load_wooldridge.py`経由で都度ロードし、`pytest.importorskip("wooldridge")`で任意扱いにする。
- 各フィクスチャJSONには`_meta`フィールドを含め、少なくとも以下を記録する。
  - `generated_at`: 生成日時（ISO 8601）
  - リファレンス実装のバージョン（例: `statsmodels_version`）
  - 使用したリファレンス実装の種類（`primary_reference`等）
  - （該当する場合）計算方法に関する注記
- フィクスチャは一度固定したら手動更新が前提（自動追従しない）。リファレンス実装側の既知のバグ修正等で意図的に更新する場合は、その理由をコミットメッセージに残す。
- **フィクスチャ生成に使うリファレンス実装（statsmodels等）は、`pyproject.toml`のdev dependenciesにバージョン固定して記載する**（例: `statsmodels==0.14.6`のように`==`で固定。範囲指定にしない）。理由: 生成スクリプトを再実行した際に、フィクスチャ生成時と異なるバージョンで異なる数値が出て混乱するのを防ぐため。

## 許容誤差

- **相対誤差1e-8程度（厳密）を基本方針** とする。
- 計算方法自体がリファレンス実装間で異なりうる手法（例: パネルのHausman検定等）は、以下の手順を取る。
  1. **基準パッケージを1つ決める**（本実装が採用する計算方法・慣習と一致するもの）。基準パッケージとは相対誤差1e-8の厳密比較を行う。
  2. **他のパッケージはクロスチェック用**とし、許容誤差を緩めて比較する（大きく乖離していないかの確認が目的で、厳密一致は期待しない）。
  3. **採用した計算方法と、どのパッケージが同じ計算方法かをテストコードのコメント・関連ドキュメントに明記する**（`docs/planning/specs/`配下の該当手法のノート、無ければ`ols-implementation-notes.md`同様の形式で新規作成）。
- **同じクロスチェック用パッケージでも、統計量・cov_typeごとに実測乖離が大きく異なる場合は、許容誤差を分けてよい**（一律に緩めると、本来検出できるはずのバグを見逃す）。分ける場合は実測値（最大相対誤差）に基づいて具体的な数値を決める。例: OLSのRクロスチェック（`test_ols_crosscheck.py`）はclassical/HC0-3/clusterで機械精度一致（実測1e-14程度）のため基本方針の1e-8を適用し、HAC（実測0.4%程度）のみ1e-2に緩めている。

## パフォーマンス比較（ベンチマーク）の方法論

- 実行時間・メモリ使用量を他ライブラリと比較する際は、**計測対象の処理範囲を対称に揃える**。比較対象ライブラリが遅延評価（lazy property）で結果を計算する設計の場合、計測コードでその結果に明示的にアクセスしないと、そのライブラリの計算コストが計測から漏れて不公平な比較になる（例: statsmodelsの`RegressionResults`は`rsquared`/`aic`/`bic`等をアクセス時に初めて計算する`cached_value`として実装している）。
- ベンチマーク作成時は、比較対象の実装がどのタイミングで何を計算するか（即時評価か遅延評価か）を事前に確認し、本実装（常に一括計算）と同じ処理範囲になるよう計測コードを書く。
- **正確性検証（テスト）とは異なり、性能比較はcov_type・オプションの全組み合わせを網羅する必要はない**。正確性検証は方針上あらゆる組み合わせで一致を確認するが、性能比較の目的はライブラリ間の相対的な傾向（速い/遅い、メモリ使用量の桁）を把握することであり、代表的な1〜2ケース（例: 計算コストが最も軽いclassicalと、最も重いcov_type）で十分とする。ただし各推定手法について性能比較を1回は作成すること自体は必須とする。

## 必須事項

- 各推定手法の実装時に、対応するリファレンス実装との比較テストを必ずセットで用意する（実装だけでマージしない）。
- ベンチマーク値を生成した際は、使用したデータセット・コード・リファレンス実装のバージョン情報を記録し、再現可能な形で残す。

## 将来的に検討する技術

- **property-basedテスト（`proptest`等）**: 現状のテストはRust側単体テスト・Pythonフィクスチャテストとも固定seed・固定シナリオでの値の一致確認にとどまり、「そのseedでは偶然問題が顕在化しないケース」を拾えない構造的な穴がある。各手法が満たすべき不変条件（例: 切片ありなら残差和は常に0、yのスカラー倍で係数も同じ倍率でスケールする等）は、個別の値比較よりプロパティとして検証する方が網羅性が高い。保険的な投資と位置づけ、手法の実装が一巡し余力があるタイミングで`engine`クレートへの導入を検討する。
